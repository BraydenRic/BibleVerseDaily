# Daily Verse: build spec

This document describes the whole system: what it does, how the repo is organized, how each piece works, and how to set it up. Hand it to Claude Code along with this repo. A working reference implementation is already here; Claude Code's job is to verify it, finish the open tasks at the bottom, and help with setup.

## 1. What it does

An automated Instagram account that posts one short scripture Reel per day at noon Pacific time.

Each post is:

- **A 12 to 30 second vertical Reel (1080x1920).** A slow-drifting, softly glowing gradient background, the verse fading in over it in a serif font, the reference underneath, and a small "Day N of M" label at the top.
- **Original ambient music.** Generated by code for every post (soft pad chords, sparse bell notes, reverb). No licensed songs, so nothing gets muted or taken down.
- **A caption** that repeats the verse (in the original language first, for traditions that show it) and reference, then a short plain-language explanation of the context (who is speaking, what is happening, what a key word means), the day count, a translation credit, and up to 5 hashtags on the last line.

Verses are not random. They follow **reading plans**: a book of scripture walked through in order, one key verse per day (the first plan is 40 days through the Gospel of Mark). When a plan finishes, the account moves to the next plan in its queue.

The system is built for **multiple traditions** later (for example Christianity, Islam, Hinduism, Buddhism, Taoism), with **one Instagram account per tradition**. Adding a tradition means adding files, not changing code.

Before anything is posted, a **preview page** shows exactly what upcoming posts will look like (video, caption, scheduled date). It is published to GitHub Pages so it can be checked from a phone.

## 2. Repo layout

```
daily-verse/

  requirements.txt                numpy, pillow, requests
  dailyverse/                     the Python package (python -m dailyverse ...)

    caption.py                    caption and overlay text
    render.py                     background, text overlay, music, ffmpeg encode
    preview.py                    builds out/preview/index.html
    instagram.py                  Instagram API calls and token refresh
    hosting.py                    gives Instagram a public URL for the video
  traditions/
    christianity/
      tradition.json              name, available texts (translation, license, attribution), base hashtags
      texts/bsb.json              full index of every verse (31,102) in the Berean Standard Bible
      plans/01-gospel-of-mark.json  40 curated verses with captions
  accounts/
    christianity.json             one file per Instagram account
  state/
    christianity.json             progress for each account (committed by the bot after every post)
  assets/fonts/                   Lora (verse) and Poppins (labels), both SIL Open Font License
  scripts/build_index_bsb.py      rebuilds texts/bsb.json from the public domain source
  .github/workflows/
    daily-post.yml                renders and posts at noon Pacific
    preview.yml                   validates plans, renders the preview page, deploys to GitHub Pages
    refresh-token.yml             refreshes Instagram tokens weekly
```

The separation that makes multiple traditions easy:

- **Tradition** = content (texts, plans, captions). Lives in `traditions/<id>/`.
- **Account** = an Instagram account that posts one tradition's plans on a schedule. Lives in `accounts/<id>.json`.
- **State** = where each account is in its queue. Lives in `state/<id>.json`.

## 3. Data formats

### 3.1 `traditions/<id>/tradition.json`

```json
{
  "id": "christianity",
  "name": "Christianity",
  "unit_name": "verse",
  "texts": {
    "bsb": {
      "title": "Berean Standard Bible",
      "short": "BSB",
      "file": "texts/bsb.json",
      "license": "Public domain since April 30, 2023",
      "source": "https://github.com/scrollmapper/bible_databases",
      "attribution": "Scripture from the Berean Standard Bible (public domain)."
    }
  },
  "ref_display": {"Psalms": "Psalm", "I Samuel": "1 Samuel", "Revelation of John": "Revelation"},
  "hashtags": "#bibleverse #dailyverse #scripture #biblestudy"
}
```

A tradition can list several texts (translations). Each plan says which one it uses. `ref_display` (optional) maps the text index's work names to the form readers expect, for the video and caption: plans reference `Psalms 23:1` (the index key) and viewers see `Psalm 23:1`.

`style` (optional) sets a tradition's look and sound:

```json
"style": {
  "audio": "silent",
  "palettes": [["#0b1f1c", "#2e6b5e", ["#e8d29a", "#7fc4b0", "#cfe7dc"]]],
  "original": {"text": "arabic", "font": "AmiriQuran-Regular.ttf", "direction": "rtl", "language": "ar",
               "on_screen": true, "in_caption": true, "line_height": 1.8}
}
```

- `audio`: `ambient` (generated pads and bells, the default), `nature` (soft wind and rain, no pitch or rhythm), or `silent`. The Quran account is silent, because many Muslims object to any sound under recited scripture.
- `palettes`: replaces the five default background palettes.
- `original`: shows the original-language text (one of the tradition's `texts`) above the translation, shaped with libraqm so Arabic joins right to left and Devanagari forms conjuncts.
  - `in_caption` (default true) also opens the caption with it, the translation right below.
  - `caption_text` names a different text for the caption (a transliteration, say). Neither account uses it now: the Quran and Gita captions show the same Arabic and Devanagari as the video.
  - `line_height` gives scripts with tall marks room.

`work_hashtags` (optional) maps a work name to its hashtag, `{"Ya-Sin": "#surahyasin"}`, and each post gets the tag of the work its verse is from. Plans that read through several surahs use a theme tag (`#tadabbur`) instead of naming one, and `validate` rejects any work tag on a verse from a different work.

### 3.2 `traditions/<id>/texts/<text>.json`

```json
{
  "id": "bsb",
  "title": "Berean Standard Bible",
  "works": [{"name": "Genesis", "chapters": [31, 25, ...]}, ...],
  "verses": {"Genesis 1:1": "In the beginning ...", "...": "..."}
}
```

Keys are `"<Work> <Chapter>:<Verse>"`. For texts organized only by chapter (the Tao Te Ching, for example), keys are `"<Work> <Chapter>"`. Work names may contain spaces ("1 Samuel").

### 3.3 `traditions/<id>/plans/<plan>.json`

```json
{
  "id": "01-gospel-of-mark",
  "title": "Gospel of Mark",
  "text": "bsb",
  "intro": "40 days through the Gospel of Mark, one verse at a time.",
  "hashtags": "#gospelofmark",
  "posts": [
    {"ref": "Mark 1:1", "caption": "Mark is the shortest of the four Gospels ..."},
    {"ref": "Mark 12:30-31", "display": "optional exact text to show instead", "caption": "..."}
  ]
}
```

- `ref` can be a single verse (`Mark 1:1`), a range in one chapter (`Mark 12:30-31`), or a chapter for chapter-only texts.
- `display` is optional. Use it only when automatic punctuation repair isn't enough (nested single quotes, for example), or to show a contiguous excerpt. Never change the words of the text; `validate` checks.
- `display_original` does the same for the original-language text. It is required whenever `display` is an excerpt, so the two languages on screen always match. It is also used to show a Quran verse 1 without the Bismillah heading that Tanzil's text attaches to it.
- Chapter-only texts can use ranges too (`Dhammapada 1-2`).
- Plans are numbered (`01-`, `02-`) so their order is obvious.

**Caption guidelines:** 2 to 4 short sentences, plain English, written for someone who is new to the text. Explain context (who, where, what just happened), define unfamiliar words, and note one interesting fact when there is one. Describe what the text says and what traditions or scholars hold, rather than telling the reader what to believe. Keep total caption length under 2,200 characters (Instagram's limit; the validator checks it).

### 3.4 `accounts/<id>.json`

```json
{
  "id": "christianity",
  "enabled": true,
  "tradition": "christianity",
  "plans": ["01-gospel-of-mark", "03-psalms", "05-acts"],
  "seasonal": [
    {"plan": "02-advent", "start": "2026-11-29"},
    {"plan": "04-john-lent", "start": "2027-02-10"}
  ],
  "timezone": "America/Los_Angeles",
  "post_time": "12:00",
  "window_minutes_before": 30,
  "window_minutes_after": 120,
  "secrets": {
    "user_id": "IG_USER_ID_CHRISTIANITY",
    "access_token": "IG_ACCESS_TOKEN_CHRISTIANITY"
  }
}
```

`plans` is a queue. `seasonal` (optional) pins plans to the calendar: day N of a seasonal plan always posts on `start + N - 1`, so Advent ends on Christmas Day however the rest of the schedule has drifted. The regular queue pauses while a seasonal plan runs and resumes after. Seasonal plans are tied to a year; add next year's dates when the time comes. `secrets` names the GitHub secrets that hold this account's credentials, so each account has its own.

`draft` (optional): marks an account whose tradition is still being set up (what `new-tradition` creates). `validate` only warns about drafts; every other account, live or not, is checked strictly.

`start_date` (optional): nothing posts before this date, even with `--force`, so code can be pushed early or a launch delayed without the hourly run posting day 1 too soon (an early day 1 would shift every later plan by a day).

`instagram_handle` (optional) labels the account on the preview page. The live account leaves it out so the public repo isn't found by searching the handle.

### 3.5 `state/<id>.json`

```json
{"plan_index": 0, "next_day": 1, "last_posted_date": null, "history": []}
```

`history` keeps the last 90 posts (plan, day, ref, date, Instagram media id).

## 4. How each piece works

### 4.1 Text lookup (`library.py`)

- `parse_ref` splits `"Mark 12:30-31"` into work, chapter, first verse, last verse.
- `lookup` joins the verses in the range.
- `balance_double_quotes` handles a common problem: a single verse often opens a quotation that closes in a later verse (or closes one that opened earlier). It adds only the missing curly quote mark. It never changes words.

### 4.2 Scheduling (`library.py`)

- `upcoming(account, count)` returns the next posts, one per day, with their scheduled local date and time. Days covered by a seasonal plan get that plan's entry for the date; every other day continues the regular queue from the account's state. If the queue runs out, nothing is scheduled until the next seasonal plan. If the account already posted today, the list starts tomorrow. The poster, the preview, and `validate` all use this, so the preview always matches what will actually go out.
- `in_window` is true when the local time is within the window around `post_time`; `is_due` adds "hasn't posted today".
- `advance` records a post. For a regular post it moves to the next day, or to the next plan when the current one is finished, using the posted plan's position in the queue. Seasonal posts leave the queue where it is.
- `display_ref` turns an index reference into the reader-facing citation using `ref_display`.

### 4.3 Rendering (`render.py`)

- **Background:** drawn with numpy at 1/5 resolution (216x384) and upscaled by ffmpeg, which keeps gradients smooth and makes rendering fast. A vertical two-color gradient that slowly shifts, six soft glowing blobs that drift and "breathe" on slow sine paths (screen blended), and a gentle vignette. The whole frame is dimmed so white text always reads. Five calm palettes (dawn, ocean, sage, lavender, dusk) rotate by day.
- **Overlay:** Pillow renders a transparent 1080x1920 PNG. The verse is set in Lora at the largest size (78px down to 34px) that fits an 860x980 box, centered, with a soft blurred shadow. Below it: a short divider and the letter-spaced reference in Poppins. At the top: "DAY N OF M".
- **Music:** numpy synthesis, deterministic per post (seeded), so re-rendering gives the same audio. Major key and chord progression chosen by seed. Soft detuned sine pads with slow swells, a low root note, sparse pentatonic bell notes, stereo reverb (convolution with decaying noise), a gentle low-pass, fade in and out, normalized to about -18 dB RMS.
- **Length:** `8 + 0.33 * words` seconds, clamped to 12 to 30.
- **Encode:** background frames are piped to ffmpeg, which scales them, overlays the text with a fade in and out, adds light film grain (prevents banding), and writes H.264 high profile, yuv420p, 30 fps, AAC 128k (Meta's Reels spec), `+faststart`. A render takes about 30 to 45 seconds on a GitHub runner.
- `render_still` makes a single JPEG frame for fast previews.

### 4.4 Posting (`cli.py`, `hosting.py`, `instagram.py`)

`python -m dailyverse post` loops over enabled accounts. For each one:

1. Skip if it already posted today (even with `--force`: one post a day) or the local time is outside its window (unless `--force`).
2. **Check Instagram first.** Read the account's secrets (so a missing one fails before rendering), then its latest 100 posts (`GET /<IG_ID>/media`). State can fall behind what's live: a run whose progress commit never landed, a publish whose reply was lost, or a run started from an old commit. If the next post is already on Instagram (a caption with the same reference line and day line), record it instead of posting it again, and check the one after. A verse that's live from a *different* post, or today's date-pinned post already out on another day, fails loudly rather than repeating it. If Instagram can't be read, nothing posts.
3. Get the next post from `upcoming`. It must be dated today: a date-pinned post is never sent early, and a day with nothing scheduled (the queue ran out before a seasonal plan) fails loudly. Render the Reel, build the caption.
4. **Host the video.** Instagram's API pulls video from a public URL (direct upload is only available with Facebook Login). `hosting.py` tries two hosts, both requiring a **public repo**:
   - `raw`: force-push the file alone to a branch named `media-<account>` and return `https://raw.githubusercontent.com/<owner>/<repo>/<commit sha>/reel.mp4`. The branch is overwritten each day so old videos don't accumulate.
   - `release`: the fallback when Instagram can't fetch the raw URL (GitHub rate-limits anonymous raw downloads). The video becomes the only asset of a pre-release tagged `reel-<account>`.
5. **Publish** with the Instagram API with Instagram Login (`graph.instagram.com`, version `v26.0`, configurable with `IG_API_VERSION`):
   - `POST /<IG_ID>/media` with `media_type=REELS`, `video_url`, `caption`, `share_to_feed=true` returns a container id.
   - Poll `GET /<container>?fields=status_code,status` every 30 seconds until `FINISHED` (give up after about 10 minutes).
   - `POST /<IG_ID>/media_publish` with `creation_id` returns the media id.
   - Network errors and 5xx responses are retried. Download/processing failures (`ERROR`, `EXPIRED`, or codes like 9004/2207052) move on to the next host with a fresh container.
6. Update `state/<account>.json` immediately, since the post is live. The workflow commits it.
7. **Read the post back** and compare its caption with what was sent. A missing caption fails the run (the post stays recorded); a reformatted one is a warning.

One account failing does not stop the others; the command exits non-zero at the end so GitHub emails a failure notice.

### 4.5 Preview (`preview.py`)

`python -m dailyverse preview --videos 3 --stills 14` renders the next 14 posts per account as stills and the next 3 as full videos, then writes `out/preview/index.html`: a phone-width page with one card per post showing the scheduled date, the media (playable video or still), and the full caption (collapsed after the first paragraph like Instagram). The first card is marked "Next up". `--stills 0` shows every remaining post.

### 4.6 Commands

```
python -m dailyverse preview [--account ID] [--videos N] [--stills N]
python -m dailyverse post [--account ID] [--force]
python -m dailyverse due [--account ID] [--force]
python -m dailyverse validate
python -m dailyverse refresh-tokens
python -m dailyverse new-tradition ID [--account ID]
```

`validate` checks that:
- every reference exists in its text and every post has a caption,
- `display` text keeps the source's exact words (an excerpt is fine),
- on-screen text fits (60 words max),
- captions are under 2,200 characters, with at most 5 hashtags, and a tag naming a book or surah only on verses from it,
- seasonal plans don't overlap and aren't also in the queue,
- no verse goes out twice: none is scheduled twice, and none repeats one from the last 90 posts (overlapping ranges count),
- no day is left without a post.

It ends by printing how far ahead each account is scheduled. Problems on disabled accounts are only warnings.

`due` prints `due=true/false` (and writes it as a GitHub step output) so the hourly workflow can stop early. `due`, `validate` and `new-tradition` need only the standard library.

## 5. GitHub Actions

### `daily-post.yml`

- Cron `50 * * * *`: hourly. Each account posts only inside its own window, in its own time zone (daylight saving included), and once a day. So one schedule serves any number of accounts in any time zones, and with a 30/120-minute window around noon there are three runs inside it every day: two automatic retries.
- Checks out the tip of `main`, not the commit that started the run, so a run that waited behind another one (or a re-run of an old run) sees the progress the latest post saved.
- First step: `python -m dailyverse due` on bare Python. Most runs stop there, in seconds. Only when something is due does it install ffmpeg and the pinned requirements and run `python -m dailyverse post`. Each account's secrets are passed to that step by name (`IG_USER_ID_X: ${{ secrets.IG_USER_ID_X }}`), never the whole secrets map: that keeps access minimal, and GitHub blocks workflows that hand over every secret (`toJSON(secrets)`) as possibly malicious. A test checks that every account's secrets are passed in both daily-post.yml and refresh-token.yml.
- Commits `state/` when it changed (pulling first in case of a concurrent push), then starts the Preview workflow. GitHub disables scheduled workflows in a public repo after 60 days without a commit; the daily commit prevents that, and if nothing has been committed for 30 days the step writes `state/heartbeat.txt` as a keep-alive commit.
- Manual run inputs: `account` and `force` (post right now), passed through environment variables, not interpolated into the script.
- Everything is pinned (runner image `ubuntu-24.04`, exact action versions, exact Python packages) so GitHub's upgrades can't change behavior mid-year.

### `preview.yml`

- Runs on pushes that touch content or code, when Daily post starts it after a post, and manually.
- Runs the tests, `validate`, then `preview`, then deploys `out/preview` to GitHub Pages.

### `refresh-token.yml`

- Weekly. Instagram long-lived tokens last 60 days and can be refreshed once they are at least 24 hours old. `refresh-tokens` gets a new token for each account and saves it with `gh secret set` using a fine-grained personal access token stored as `GH_PAT`. Accounts that aren't live yet are included once they have a token, so a token can't expire while its account waits to launch.

## 6. One-time setup

1. **Instagram:** create the account, then in the app go to Settings, Account type and tools, and switch to a professional account (Creator is fine). The publishing API only works with professional accounts.
2. **Meta developer app:** at developers.facebook.com, create an app with the Instagram use case, "API setup with Instagram login". Add the Instagram account (give it a tester or admin role on the app if asked) and generate an access token with `instagram_business_basic` and `instagram_business_content_publish`. App review is not needed to post to your own account.
3. **Find the account id:**
   `curl "https://graph.instagram.com/v26.0/me?fields=user_id,username&access_token=TOKEN"` and use `user_id`.
4. **GitHub repo:** create a **public** repo and push this code. In Settings:
   - Secrets and variables, Actions: add `IG_USER_ID_CHRISTIANITY`, `IG_ACCESS_TOKEN_CHRISTIANITY`, and `GH_PAT` (a fine-grained token for this repo with Secrets read and write).
   - Pages: set Source to "GitHub Actions".
   - Actions, General: allow workflows to read and write.
5. Optionally put the handle in `accounts/christianity.json` as `instagram_handle` (it only labels the preview page; leaving it out keeps the public repo from being found by the handle).
6. Run **Preview** manually and open the Pages link on your phone.
7. Run **Daily post** manually with `force` on to publish day 1 and confirm everything works. From then on it posts itself at noon.

## 7. Adding another tradition

`python -m dailyverse new-tradition <id>` (optionally `--account <account id>`) creates every file below as a template, with the account **disabled** so nothing posts and `validate` only warns until it's ready. Then:

1. Fill in `traditions/<id>/tradition.json`: pick a translation whose license allows reposting (prefer public domain), and record the license and source.
2. Write a small script like `scripts/build_index_bsb.py` that downloads the text and saves `traditions/<id>/texts/<text>.json` in the format above.
3. Write the first plan in `traditions/<id>/plans/01-<name>.json` and list it in the account's `plans`.
4. Create a separate Instagram account, add it as an Instagram Tester on the same Meta app, generate its token, and add its two secrets (the names are in the account file).
5. Pass the account's secrets to the workflows by name (two lines in daily-post.yml, one in refresh-token.yml; `new-tradition` prints them and a test checks). Run `validate` and check the preview, then set `"enabled": true`. Time zones and post times need no workflow changes.

Traditions set up so far, and candidates (verify any license yourself before using; US public domain status may differ elsewhere):

| Tradition | Text | Translation | Status |
|---|---|---|---|
| Islam | Quran | Marmaduke Pickthall, 1930 (public domain), with Tanzil's Arabic | set up: `islam` |
| Hinduism | Bhagavad Gita | Annie Besant, 1895/1922 (public domain), with Sanskrit from gita/gita | set up: `hinduism` |
| Buddhism | Dhammapada | F. Max Müller, 1881 ([Gutenberg #2017](https://www.gutenberg.org/ebooks/2017)) | candidate: the runner-up, ideal text but a smaller audience |
| Taoism | Tao Te Ching | James Legge, 1891 | candidate |

Islam and Hinduism were chosen for audience size on Instagram, short standalone verses, and public-domain verse-numbered English. Their accounts post at local noon for their main audiences (London and Kolkata).

Things to respect when expanding:

- Keep one account per tradition. Don't mix traditions in one feed.
- Many Muslims consider only the Arabic text to be the Quran itself, so label English as "a translation of the meaning" and consider showing the Arabic as well.
- Have captions for each tradition reviewed by someone who practices it before they go live.
- Background palettes and fonts can be overridden per tradition later if a different visual feel fits better.

4. **Year two:** queue the next plans, and add next year's seasonal dates (Advent starts Nov 28, 2027; Lent starts Mar 1, 2028, and Easter is Apr 16, 2028; Islamic and Hindu dates move about 11 days earlier each solar year, so look them up).

## 9. Constraints and gotchas

- The repo must stay public for video hosting (raw URLs and release assets) and the free Pages preview to work.
- Meta's docs give 100 (and elsewhere 50) API-published posts per account per 24 hours, far above what this uses.
- Instagram needs the video URL reachable when the container is created; the script waits for it to return 200 first.
- Reels published through the API cannot use songs from Instagram's in-app music library. The generated audio is the replacement.
- Rendering is deterministic per post (seeded), so previews match what is posted.
- Times are always handled with `zoneinfo` in the account's own time zone.
